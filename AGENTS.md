# Grantline Working Memory

## Purpose

Grantline is programmable financial authority for AI agents. The agent proposes an action, while Grantline determines whether that action is authorised under an active Mandate and its surrounding conditions.

This file is the project-wide working memory for future agents and contributors. Keep implementation details in the nearest package-level `AGENTS.md` and keep this file focused on shared context, boundaries, decisions, and handoffs.

## Product invariants

- The agent decides what it wants to do; Grantline decides whether it is allowed to do it.
- Vault capital must be unreachable through an agent-controlled bypass path.
- `ALLOW`, `ESCALATE`, and `DENY` are authorisation outcomes, not execution outcomes.
- An authorised action can still fail during downstream execution, and that must remain distinguishable from `DENY`.
- Delegated authority may become narrower, never broader, than its parent authority.
- Revocation preserves historical lineage while preventing future authority use.
- Public-facing product copy uses UK English, including `authorisation`, `authorised`, and `tokenised`.

## Current status

The repository contains the product brief, the Next.js/Fumadocs website foundation, and the working contracts loop. The website has the canonical category-first landing page, concept docs, the current Security model, enforcement and execution docs, integrator guides, contract reference pages, a planned Guardians concept page, one Roadmap page, Fumadocs search and LLM routes, metadata, favicon, robots, sitemap, ESLint, Vercel Web Analytics, and reproducible Bun setup; its package-local handoff is in `website/AGENTS.md`. Its canonical site URL is resolved on the server from `NEXT_PUBLIC_SITE_URL` with a `VERCEL_URL` fallback, while browser-safe repository and X links live separately so deployment-only environment variables cannot break hydration. The contracts workspace now has one breaking Grantline architecture directly under `contracts/src`, with the Vault, nested mandate rules, typed ActionPlan and signatures, `ALLOW`/`ESCALATE`/`DENY` evaluation, full-plan escalation storage, owner approval or denial, shared nonce replay protection, targeted nonce cancellation and escalation reservations, executor re-evaluation, native amount and native-asset USD bounds, native-balance and native-USD Preflight checks, per-Vault and inherited Mandate pause controls, onchain execution records, deployment verification with runtime-hash validation, and parent/child delegation with inherited authority and lineage revocation. Native-asset USD rules and Preflight reserve floors use one manifest-defined Chainlink feed and its declared decimals, count native plus the canonical wrapped-native token for action valuation, value only actual native balance for USD Preflight, and interpret thresholds as whole dollars; deployments without a feed reject nonzero native-USD rules, while generic token valuation and oracle staleness enforcement remain deferred. `Grantline` is the user-facing facade, while the non-upgradeable `GrantlineAdmin` coordinator owns module proxies and performs protocol upgrades, Vault template management, controller reassignment, adapter-input validation, and wiring validation; its protocol-admin authorization derives from `Grantline.owner()` so ownership handoffs cannot strand or preserve upgrade authority, while Vaults remain owned by Grantline for custody and pause controls but use the admin coordinator as their UUPS upgrade authority. MandateRegistry remains authoritative for repeated Mandate, delegation, and nonce-cancellation checks reached through the facade. The optimized Grantline runtime is currently 21,524 bytes against the 24,576-byte EIP-170 limit. `VaultExecutor` also has one storage-backed reentrancy lock across normal and escalated entrypoints, so a recipient cannot start a nested plan against a stale balance snapshot. The Grantline-only local suite now has 179 passing tests covering evaluator boundaries, delegation narrowing, custody and cross-Vault isolation, execution atomicity and reentrancy, token return conventions, escalation state transitions, targeted nonce cancellation, admin separation, proxy upgrades, pause semantics, mandate validity windows, native-asset USD valuation, USD Preflight reserve valuation, arithmetic overflow, deployment verification, SWAP route validation and execution, and fuzzed nonce, deadline, limit, and digest properties. The latest source-focused coverage is 85.98% lines, 54.93% branches, and 99.57% functions across `contracts/src`; deployment and integration scripts are excluded from those percentages. The replacement single-pass integration flow is written with reserved deployer, agent, and delegated-agent identities and has completed successfully against X Layer testnet chain 1952; the tracked `contracts/deployments/xlayer-testnet.json` retains the live pre-feature deployment identity while following the current manifest schema without dynamic Vault snapshots. SWAP v1, targeted nonce cancellation, native-asset USD rules, and USD Preflight reserve floors are implemented for a future fresh deployment, while the current X Layer stack remains unchanged and exposes none of those additions. Destination and capability policies, shared cumulative budgets, sponsored transaction submission, offchain indexing, Guardian enforcement, generic token USD valuation, oracle staleness enforcement, behavioural history, policy commitments, protocol-wide pause controls, and receipt assembly remain deferred.

The current X Layer deployment remains unchanged until a fresh deployment is chosen; native-USD Preflight reserve floors use the same manifest feed, decimals, whole-dollar thresholds, conservative rounding, and fail-closed valuation path as native-asset USD Mandate rules, while valuing only projected actual native balance. Public evaluation now reports used or reserved nonces as `DENY`, while approved escalated execution uses an explicit internal evaluator mode for its matching reservation and retains executor-side replay checks. The optimized Grantline runtime is currently 21,524 bytes against the 24,576-byte EIP-170 limit.

Sponsored submission remains deferred because the integration evidence uses the agent as the actual transaction submitter; users currently submit the transaction and pay its gas directly.
