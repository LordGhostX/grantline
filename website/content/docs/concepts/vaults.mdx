<Callout type="info" title="Development status">
  The current X Layer deployment uses non-upgradeable contracts. While Grantline
  remains under active development, the next managed deployment is expected to
  use upgradeable Vaults so custody and enforcement issues can be corrected.
  The protocol admin controls those upgrades, which is part of the current trust
  model. Once the Vault interface and enforcement stack stabilise, the intended
  direction is a non-upgradeable Vault boundary.
</Callout>

A Vault holds the capital that a Mandate governs. An agent receives permission to propose actions against that capital; it does not receive ownership of the Vault or a private-key path around its controls.

## Owner and authority

The owner remains responsible for the Vault and its administration. Grantline's execution authority acts for the Vault only through the controls placed around the [Mandate](/docs/concepts/mandates) and [Action Plan](/docs/concepts/action-plans).

This separates custody from operation. An allowed action can proceed without the owner signing every routine transaction, while an action that crosses a configured boundary can require the owner's approval through [Escalation](/docs/enforcement/escalation).

## A boundary around capital

The Vault is the final controlled boundary between an authorised proposal and capital movement. Its generic execution surface accepts calls only from its configured authority, so an agent cannot turn a valid signing identity into unrestricted access to the Vault.

Vaults can support different kinds of capital, actions, and execution integrations over time, but the custody boundary remains the same: authority to act does not become ownership of the capital.

See [Mandates](/docs/concepts/mandates) for the authority applied to a Vault and [Decisions](/docs/concepts/decisions) for the outcomes that precede execution.
