title: Build and sign an Action Plan
description: Construct the current TRANSFER Action Plan shape and sign its EIP-712 digest without relying on a Grantline SDK.

<Callout type="info" title="Current integration">
  Grantline does not yet publish an SDK or API. This guide shows the current
  contract shape with external ABI and wallet tooling; it is useful for testnet
  integration, but it is not a Grantline package to install.
</Callout>

The current contracts accept one typed action, `TRANSFER` version `1`. The example below constructs the proposal, encodes its transfer, signs it, and checks the result before choosing normal execution or escalation.

## Human-readable plan

An integrator can represent the current plan like this before encoding it for the contract:

```json
{
  "mandateId": "1",
  "agent": "0xAgent",
  "nonce": "1",
  "deadline": "0",
  "actions": [
    {
      "type": "transfer",
      "version": 1,
      "asset": "native",
      "to": "0xRecipient",
      "amount": "1000000000000000000"
    }
  ]
}
```

This JSON is a readable representation. The contract action uses enum value `0` for `TRANSFER`, and native `asset` is encoded as the zero address. The amount above is `1 OKB` in raw base units. Token amounts must use the token's own raw base units.

## Encode the action parameters

The current `TransferParameters` tuple is `(address asset, address recipient, uint256 amount)`. Solidity `abi.encode` produces the `bytes` value placed in the action's `parameters` field.

```ts
// Illustrative TypeScript using viem as an external wallet and ABI utility.
import { encodeAbiParameters, parseEther, zeroAddress } from "viem";

const asset = zeroAddress;
const recipient = "0xRecipient" as `0x${string}`;

const parameters = encodeAbiParameters(
  [{ type: "address" }, { type: "address" }, { type: "uint256" }],
  [asset, recipient, parseEther("1")],
);

const actionPlan = {
  mandateId: 1n,
  agent: agentAddress,
  nonce: 1n,
  deadline: 0n,
  actions: [
    {
      actionType: 0,
      version: 1,
      parameters,
    },
  ],
} as const;
```

The evaluator checks that the parameter bytes are non-empty and exactly the current transfer shape before decoding them. A zero recipient or zero amount is invalid.

## Sign the EIP-712 message

The domain is bound to the deployed evaluator and chain. `evaluatorAddress` must come from the current deployment manifest, and `agentAddress` must be the address bound to the Mandate and the wallet that signs.

```ts
const domain = {
  name: "Grantline",
  version: "1",
  chainId: 1952,
  verifyingContract: evaluatorAddress,
} as const;

const types = {
  Action: [
    { name: "actionType", type: "uint8" },
    { name: "version", type: "uint8" },
    { name: "parameters", type: "bytes" },
  ],
  ActionPlan: [
    { name: "mandateId", type: "uint256" },
    { name: "agent", type: "address" },
    { name: "nonce", type: "uint256" },
    { name: "deadline", type: "uint256" },
    { name: "actions", type: "Action[]" },
  ],
} as const;

const signature = await walletClient.signTypedData({
  account: agentAddress,
  domain,
  types,
  primaryType: "ActionPlan",
  message: actionPlan,
});
```

The signature covers the complete ordered plan. Changing the Mandate, agent, nonce, deadline, action order, version, or encoded parameters changes the digest. The evaluator also rejects high-`s` signatures and signatures that recover to an address other than the Mandate agent.

## Evaluate before submitting

The evaluator is a read-only contract call and returns the decision, failure code, failed action index, aggregate amounts, valuation-skip flag, and projected native balance. Use it to explain the result before deciding whether to submit the normal executor call or the escalation path.

An `ALLOW` result can be submitted to `VaultExecutor.execute`. An `ESCALATE` result can be submitted to `EscalationManager.submit`, after which the Vault owner decides whether to approve or deny the stored digest. A `DENY` result should not be submitted as an execution attempt because the executor will revert before calling the Vault.

See [Action Plans](/docs/concepts/action-plans), [Action commitments, signatures and nonces](/docs/enforcement/action-commitments-signatures-and-nonces), and [Decisions and failures](/docs/reference/decisions-and-failures) for the exact current model.
