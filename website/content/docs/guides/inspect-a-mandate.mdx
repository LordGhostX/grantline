---
title: Inspect a Mandate
description: Use read-only calls to inspect a Mandate, its effective rules, Preflight boundary, and authority lineage.
---

This guide uses the tracked X Layer testnet manifest and Foundry's `cast` commands. It does not change contract state, so it is safe to use with a public RPC and a read-only environment.

## Load the deployment values

Run this from `contracts/` after copying `.env.example` to `.env` and setting the public RPC and manifest values. Keep private keys out of this workflow.

```sh
cd contracts
set -a
source .env
set +a

MANIFEST="$DEPLOYMENT_MANIFEST_PATH"
REGISTRY="$(jq -r '.mandateRegistry.address' "$MANIFEST")"
RPC="$XLAYER_TESTNET_RPC_URL"
MANDATE_ID=1
```

The manifest is the source of truth for the registry address. Do not copy an address from an old transaction log, because a later deployment may use a different stack.

## Read the Mandate record

First check the registry count and the stored record:

```sh
cast call "$REGISTRY" \
  "mandateCount()(uint256)" \
  --rpc-url "$RPC"

cast call "$REGISTRY" \
  "getMandate(uint256)((uint256,address,address,address,uint256,uint8,uint8,(bool,uint256,uint256,bool,uint256,uint256,bool),(uint256,bool),uint64,uint64))" \
  "$MANDATE_ID" \
  --rpc-url "$RPC"
```

The returned Mandate contains its ID, owner, Vault, agent, parent ID, delegation depth, status, `MandateRules`, `PreflightRules`, creation timestamp, and revocation timestamp. The status enum is `0` for `ACTIVE` and `1` for `REVOKED`.

The amount fields are integer base units. Native values use OKB's 18-decimal base unit, so `1000000000000000` is `0.001 OKB`. USD values use 1e18-scaled USD units when a valuation is available. Convert values for display only; send the original integers when calling contracts.

## Check effective authority

Stored child rules are not the whole authority that the evaluator uses. Read the active lineage and the effective rules separately:

```sh
cast call "$REGISTRY" \
  "getLineage(uint256)(uint256[])" \
  "$MANDATE_ID" \
  --rpc-url "$RPC"

cast call "$REGISTRY" \
  "isLineageActive(uint256)(bool)" \
  "$MANDATE_ID" \
  --rpc-url "$RPC"

cast call "$REGISTRY" \
  "getEffectiveRules(uint256)((bool,uint256,uint256,bool,uint256,uint256,bool))" \
  "$MANDATE_ID" \
  --rpc-url "$RPC"

cast call "$REGISTRY" \
  "getEffectivePreflightRules(uint256)((uint256,bool))" \
  "$MANDATE_ID" \
  --rpc-url "$RPC"
```

The effective amount minimum is the greatest active ancestor minimum, and the effective non-zero maximum is the tightest active ancestor maximum. Escalation and delegation permissions remain enabled only when every relevant Mandate enables them. The effective Preflight floor is the greatest active ancestor floor, and its escalation permission is also inherited through the lineage.

If `isLineageActive` returns `false`, a proposal from the Mandate cannot be authorised even when the stored Mandate record itself still reports `ACTIVE`. That is how ancestor revocation reaches descendants without rewriting every child record.

## Read the Vault context

The Mandate points to a Vault. Read its owner, current authority, native balance, and the current testnet chain before interpreting the Mandate as executable:

```sh
# Set this to the decoded `vault` field returned by getMandate.
VAULT=0x...

cast call "$VAULT" "owner()(address)" --rpc-url "$RPC"
cast call "$VAULT" "authority()(address)" --rpc-url "$RPC"
cast balance "$VAULT" --rpc-url "$RPC"
```

A Mandate does not become executable merely because its record and rules look valid: the active lineage, evaluator, current authority, nonce state, and projected balance still apply at execution time.

See [Mandates](/docs/concepts/mandates) for the product model and [mandate rules](/docs/reference/mandate-rules) for the exact current fields.
