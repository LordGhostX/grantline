The current X Layer testnet deployment is recorded in `contracts/deployments/xlayer-testnet.json`. The manifest contains the expected chain, contract addresses, dependency wiring, Vault owner and authority, evaluator valuation settings, deployment transactions, and runtime code hashes.

## Current wiring

```text
MandateRegistry ← MandateEvaluator ← EscalationManager
       ↑                 ↑                   ↑
       └──────── VaultExecutor ──────────────┘
                         ↓
                       Vault
```

> Arrows show contract dependency or call direction.

The roles are separate so each part has one job:

- `Vault` holds native and token capital, exposes owner custody operations, and accepts generic execution only from its configured authority.
- `MandateRegistry` stores Mandates, lineage, effective rules, nonce usage, and escalation reservations.
- `MandateEvaluator` reads the registry and returns a structured authorisation result without moving capital.
- `EscalationManager` stores complete escalated plans, accepts permissionless submission, and restricts approval or denial to the Vault owner.
- `VaultExecutor` binds the evaluator, escalation manager, registry, and Vault execution path, then translates supported actions into atomic Vault calls.

## Verification before use

Load the contracts environment and run the read-only verification script:

```sh
cd contracts
set -a
source .env
set +a
forge script script/VerifyDeployment.s.sol:VerifyDeployment --rpc-url xlayer_testnet
```

`VerifyDeployment` checks the expected chain and each recorded runtime hash. It also checks the Vault owner and authority, the evaluator's registry and USD settings, the escalation manager's evaluator, and the executor's evaluator and manager. A mismatch stops verification instead of allowing an internally inconsistent manifest to look valid.

Authority configuration uses the same manifest checks before broadcasting. The Vault owner must explicitly set the executor as authority; the executor does not configure itself and cannot execute a Mandate against a different Vault than the one recorded in that Mandate.

## Updating a deployment

Deploy a replacement component and verify its runtime code and dependency wiring before treating it as current. Update the tracked manifest only after the broadcast succeeds and the resulting address, transaction, authority, and code hash have been checked. This ordering keeps a failed or misdirected authority change visible instead of hiding it behind an edited record.

Use the addresses from the current manifest rather than an old integration log. Deployment scripts verify those values, and the relevant network page should be updated whenever the deployment changes.

See [X Layer testnet](/docs/execution/networks/x-layer-testnet) for network-specific details and [Enforcement boundary](/docs/enforcement/enforcement-boundary) for how the deployed components constrain execution.
